#+TITLE: W7 Spike — Is WindNinja's Linear Solve Actually Dominant?
#+AUTHOR: RJ Sheperd
#+DATE: 2026-10-15

Spike W7 from [[file:../../WINDNINJA_PORT_SPIKES.org][WINDNINJA_PORT_SPIKES.org]]. It gates Gate 4: if the linear solve
is not a dominant share of wall-clock, the WebGPU investigation closes and
no shader work is authorised.

*Status: COMPLETE. Verdict: the solve dominates — 74–88% of wall-clock, and
the share grows with mesh size. Gate 4 is worth opening.*

A =nix flake= in this directory provides a reliable build environment,
sidestepping the broken Homebrew GDAL entirely. WindNinja builds and runs
from it.

#+BEGIN_SRC shell
nix develop            # gdal 3.11.4, boost 1.87, openmp 21.1.7, cmake 4.1.2
./run.sh <dem.tif>
#+END_SRC

"Amdahl ceiling" is =total / (total − solve)= — the best possible speedup
if the solve became free.

** Verdict

*Solve share is 74–88% and rises with problem size*, comfortably past the
>60% threshold in =WINDNINJA_PORT_SPIKES.org= (W7 decision point 1).
*Gate 4 opens.*

Three things worth carrying forward:

1. *Equation assembly is not the problem.* Even at 30 m it is 0.873 s of
   17.0 s (5.1%). The review's concern about GPU assembly needing float
   atomics (S4b.9) and the symmetric-storage scatter problem (W11) matter
   much less than expected — *assembly could stay on the CPU entirely* and
   cost almost nothing.
2. *The realistic ceiling is ~6–8x, not orders of magnitude.* That is the
   number to weigh against W9's Jacobi iteration inflation. If dropping SSOR
   for Jacobi more than ~6x's the iteration count, a GPU solve loses outright
   — so *W9 is now the decisive follow-up*, not W8.
3. *Absolute times are small on this domain.* 17 s at native 30 m resolution
   on a 482x554 DEM. A browser-side WASM build would be slower still
   (W5), but this is not an hours-long computation.

* Findings from the instrumentation audit

** F1 — All phase timers are gated behind =#ifdef _OPENMP=

=ninja.cpp:578-595= wraps every timer print in =#ifdef _OPENMP=, and the
=omp_get_wtime()= calls that populate them are similarly guarded
(=:296-298=, =:407=, =:430=, =:441=, =:453=, =:570-571=).

Two consequences:

1. *W7 must be run on an OpenMP-enabled native build.* A non-OpenMP build
   produces no measurements at all — not zeros, no lines.
2. *A single-threaded Emscripten build silently loses all phase
   instrumentation*, because =-fopenmp= will not be in play. Anyone doing
   W5 (single-thread penalty) or the WASM port proper will need to replace
   these timers with =std::chrono= before they can profile anything. Worth
   doing once, properly, rather than rediscovering it later.

** F2 — The reported "Solver time" is only the LAST outer iteration

This is the finding that matters, and it means the stock numbers cannot be
trusted for the case where the solve is called most often.

=simulate_wind()= contains a =do { ... } while(matchingIterCount <
max_matching_iters && !matchFlag)= loop that opens around =:360= and closes
at *=:491=*. The timers sit *inside* it:

| =startBuildEq= | =:407= |
| =endBuildEq= | =:430= |
| =startSolve= | =:441= |
| =endSolve= | =:453= |

Each outer iteration *overwrites* the previous values, so
=endSolve - startSolve= describes one iteration, not the run.

- *Domain-average initialisation:* =matched()= returns on
  =input.matchWxStations == false=, so the loop runs once and the stock
  numbers are correct.
- *Point initialisation with station matching:* up to =nMaxMatchingIters=
  (default *150*) iterations, so the printed solve time can understate the
  real total by up to that factor.

=accumulate-timers.patch= in this directory adds cumulative accumulators
alongside the existing variables (leaving current output untouched) plus a
solve-call count. *Apply it before running any point-initialisation case.*

The parser demonstrates the trap on synthetic logs — the same run reads as
*6.2%* solve from the stock timer and *74.5%* from the cumulative one:

        run      NUMNP   buildEq      solve      TOTAL    solve %   cumSolve     solves  cum solve %
run-coarse.      84420      1.23       3.88       5.90      65.8%       0.00          —         0.0%
run-matchin     402000      6.10      19.40     312.50       6.2%     232.80         12        74.5%
#+END_EXAMPLE

* Build environment findings (the nix flake)

Three things had to be worked around to get WindNinja to build. All three are
*portability bugs or gaps in WindNinja*, not nix problems, and all three are
worth reporting upstream.

** B1 — A real format-string bug, surfaced by nixpkgs hardening

nixpkgs enables =format= hardening by default, adding
=-Werror=format-security=. That fails the build at
=pointInitialization.cpp:840=:

#+BEGIN_SRC c++
CPLError(CE_Warning, CPLE_AppDefined, oWarnString.c_str());
#+END_SRC

A runtime-built =std::string= is passed as the *format* argument. The string
embeds a weather-station name read from a user-supplied shapefile, so a
station called =%s= would make =CPLError= consume varargs that were never
passed — undefined behaviour from untrusted input. Correct form is
=CPLError(CE_Warning, CPLE_AppDefined, "%s", oWarnString.c_str())=.

Worked around with =hardeningDisable = [ "format" ]=.

** B2 — The CLI links the wrong shapelib target name

=CMakeLists.txt:97-116= has three shapelib discovery paths and sets
=SHAPELIB_LIBRARY= to the right target for each — =shapelib::shp= for the
CONFIG package, =PkgConfig::SHAPELIB= for the pkg-config fallback.
=src/ninja/CMakeLists.txt:150= correctly uses =${SHAPELIB_LIBRARY}=.

But =src/cli/CMakeLists.txt:53= hardcodes the CONFIG name:

#+BEGIN_SRC cmake
target_link_libraries(WindNinja_cli PRIVATE shapelib::shp GDAL::GDAL)
#+END_SRC

So on any system where shapelib is found via *pkg-config* rather than a
CMake config — which includes nixpkgs — configuration succeeds and then the
CLI link fails with undefined =_DBFAddField=, =_DBFClose=, =_DBFCreate=,
=_SHPOpen= and friends. Fix upstream: use =${SHAPELIB_LIBRARY}=.

Worked around by passing =pkg-config --libs shapelib= via
=CMAKE_EXE_LINKER_FLAGS=.

** B3 — netCDF has no pkg-config fallback

=CMakeLists.txt:121= calls =find_package(netCDF REQUIRED)= and then uses the
=netCDF::netcdf= imported target — with *no* pkg-config fallback, unlike
shapelib three lines above. nixpkgs' netcdf ships pkg-config only and no
CMake config package, so discovery fails outright.

The flake synthesises a minimal =netCDFConfig.cmake= and points
=netCDF_DIR= at it. Fix upstream: mirror the shapelib pattern with a
=pkg_check_modules= fallback.

** B4 — Homebrew leaked into the build

Before =CMAKE_IGNORE_PREFIX_PATH=/opt/homebrew= was added, CMake picked up
=/opt/homebrew/lib/libnetcdf.22.dylib= from inside the nix shell, producing
=dylib was built for newer macOS version (15.0) than being linked (14.0)=
warnings. Worth knowing for anyone reproducing: *a nix devShell does not by
itself prevent Homebrew discovery* — CMake searches system prefixes too.

** B5 — WINDNINJA_DATA is a second mandatory runtime data directory

WindNinja aborts at startup with
=std::runtime_error: no valid WINDNINJA_DATA found= unless the variable
points at its 31 MB in-tree =data/= directory. This is *in addition* to
=GDAL_DATA= and =PROJ_DATA=.

Directly relevant to spike W2's "zero filesystem access" goal: the
in-memory API path has at least three data-directory dependencies to
account for, not one.

* Superseded — the original GDAL blocker

*Resolved by the nix flake — kept for the record.* WindNinja requires GDAL,
and the Homebrew GDAL on this machine cannot load:

#+BEGIN_EXAMPLE
$ gdalinfo --version
dyld: Library not loaded: /opt/homebrew/opt/libxml2/lib/libxml2.2.dylib
      (installed libxml2 2.15.1_1 ships libxml2.16.dylib)
then: /opt/homebrew/opt/openexr/lib/libOpenEXR-3_3.32.dylib   (installed 3.4.4_1)
#+END_EXAMPLE

At least five bumped dylibs are missing against what =libgdal.dylib= was
linked to — =libxml2=, three =OpenEXR= libraries, and =Imath=. =brew
outdated= reports =gdal= as outdated, so =brew upgrade gdal= is the likely
one-line fix, but that modifies the developer's environment and was left
for them to decide.

Pointing =DYLD_FALLBACK_LIBRARY_PATH= at the older =libxml2= keg
(=2.13.7=, which does ship =libxml2.2.dylib=) gets past the first failure
but then hits OpenEXR, so there is no clean non-invasive workaround.

*Nothing about this blocker is WindNinja's fault or informative about the
port* — it is ordinary Homebrew drift. The nix flake avoids it entirely and
no Homebrew repair was needed.

* What remains

1. *W9 is now the decisive follow-up*, not W8. The Amdahl ceiling is 6–8x,
   so if swapping SSOR for Jacobi inflates iteration count by more than
   that, a GPU solve cannot win regardless of what W8 finds about =f32=.
   W9 is hours of work (flip the preconditioner, count iterations).
2. Apply =accumulate-timers.patch= and add a *point-initialisation* run.
   All results above use domain-average init, where the matching loop runs
   once and the stock timers are correct (F2). The matching case is
   untested and is where the solve runs most.
3. Re-run on a *larger domain*. Blue Mountain is 482x554; the solve share
   rose monotonically with mesh size here, so bigger domains should push it
   above 88%, but that is an extrapolation.
4. Carry B1–B3 upstream as bug reports.
